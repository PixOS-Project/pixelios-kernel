## 1. The four 4389 deltas bwfm lacks (requirement 1)

### 1a. RAM base 0x200000 (`CA7_4389_RAM_BASE`)
- bwfm: `bwfm_chip_tcm_rambase` ends with the 4387 case `0x740000` and a `default:` that only prints `unknown chip` (so `ch_rambase` stays 0) [src W/bwfm.c:1605-1611]; the firmware copy and the last-word clear use `ch_rambase` [src W/if_bwfm_pci.c:829-834]. The run showed `unknown chip: 17289` for 0x4389 [src HX:14].
- DHD: SYS_MEM branch `case BCM4388_CHIP_ID: case BCM4389_CHIP_ID: bus->dongle_ram_base = CA7_4389_RAM_BASE` [src D/dhd_pcie.c:2340-2353 (read: the case is at 2348-2351)]; `#define CA7_4389_RAM_BASE (0x200000)` [src D/include_sbchipc.h:4169]. Its `default:` also falls back to `0x200000` with a warning [src D/dhd_pcie.c:2354-2358].
- brcmfmac: no 4389 case; 4387 = 0x740000 is a different part, do not copy [src R37:70, citing B/brcmfmac-chip.c:746-747].
- Our own research: R37:70 (base), R37:72 (RAM spans `0x200000..0x200000+ramsize-1`, DHD attach fails if ramsize > 4 MiB, `D/dhd_pcie.c:2453-2457`).
- TCM window consequence: DHD maps BAR2 as "bar1" and sets `bar1_switch_enab` (the cfg 0x84 move itself is in the TCM accessor, R37:73) [src D/dhd_pcie.c:6162-6180]. Our BAR2 is 4 MiB [obs R28, R37:72], so RAM from 0x200000 needs cfg 0x84 = 0 for the first 2 MiB and a window move for the rest if `ramsize > 2 MiB` [src R37:72]. cfg 0x84 = 0 was observed at S30 [obs R36 s.0 via R37:13]. Total RAM size is NOT yet known (see 1b), so whether the 1.72 MiB firmware plus NVRAM fit below 0x400000 is **Unknown U3**.
- Verdict: port adds `case 0x4389: rambase = 0x200000`. [src] complete; the only unverified part is "RAM actually decodes at 0x200000" (U3).

### 1b. SYS_MEM rev 9 coreinfo masks and bank size formula
- bwfm uses the OLD SOCRAM mask for SYS_MEM too: `SRNB_MASK 0xf0 >> 4` [src W/bwfmreg.h:102-103], loops banks `0..nb-1`, writes `bankidx = (MEMTYPE_RAM(0) << 8) | i` [src W/bwfm.c:1517-1521; W/bwfmreg.h:106-110], banksize `((bankinfo & 0x7f)+1) * 8192` [src W/bwfm.c:1524-1525; W/bwfmreg.h:112-113], no ROM-bank skip.
- DHD (`si_corerev < 12`): `nrb = (coreinfo & SYSMEM_SRCI_ROMNB_MASK) >> SHIFT`, `nb = (coreinfo & SYSMEM_SRCI_SRNB_MASK) >> SHIFT` [src D/siutils.c:7036-7041]; masks `SYSMEM_SRCI_ROMNB_MASK 0x3e0` shift 5, `SYSMEM_SRCI_SRNB_MASK 0x1f` shift 0 [src G/g4389-include_sbsysmem.h:115-118]; the `NEW_*` masks `0xff000000`/`0xff0000` are rev >= 12 only [src G/g4389-include_sbsysmem.h:120-123]. SYS_MEM is rev 9 [obs R40:14, from the EROM decode of w3a-n33].
- Bank walk: `for i < nb: memsize += sysmem_banksize(regs, i + nrb)` (ROM banks skipped) [src D/siutils.c:7049-7050]; `sysmem_banksize` writes `bankidx = idx` (no memtype field), waits `SI_BANKINFO_DELAY_USEC`, reads `bankinfo`, `banksize = SYSMEM_BANKINFO_SZBASE * ((bankinfo & SYSMEM_BANKINFO_SZMASK) + 1)` [src D/siutils.c:6966-6976]. `SZBASE = 8192`, `SZMASK = 0x7f`, `bankidx` reg `0x10`, `bankinfo` reg `0x40` [src G/g4389-include_sbsysmem.h:181, 163, 167, 166].
- Observed on the chip: `coreinfo = 0x00000115` [obs w3a-n35, `L35` R35 row 1379; `L36` R35 row=1379 rd=0x00000115] = DHD decode nrb 8 (0x115 & 0x3e0 = 0x100 >> 5), nb 21 (0x115 & 0x1f); the brcmfmac/bwfm decode (0xf0 >> 4) gives 1 [src R40:159-160]. So bwfm's `nb = 1`, bank index 0 (a ROM bank here, since nrb = 8 per the DHD decode) and RAM size = size of bank 0 would be WRONG on this chip.
- One bank read happened: `bankinfo = 0x0F00039F` at row 1383 of the unselected state [obs `L36` R35 row=1383]; it is "the bankinfo of the unselected bank", informational only [src R40:162]. Do not derive a size from it.
- Bank size of the RAM banks (index 8..28) and the total: **never read** (bankidx writes for nrb != 0 are refused by the shim's `memw_ok` [src K/shim/wlanlink.c:219-236 (bankidx rule: `(pred & 0x3E0) == 0`)]). Per-bank size uniformity is a guess [src R40 s.4 labelled guess].
- A second route avoids reading banks: bwfm overrides `ch_ramsize` from the firmware image if the 4 bytes at image offset `BWFM_RAMSIZE 0x6c` equal `BWFM_RAMSIZE_MAGIC 0x534d4152` ("SMAR"), taking the next dword [src W/if_bwfm_pci.c:515-520; W/if_bwfm_pci.h:108-109]. Whether the Google 4389 `fw_bcmdhd.bin` carries that magic is **Unknown U4** (no blob byte has been read by policy, R39 header; settle with an 8-byte read at 0x6c of the host copy, needs the research-34 s.3 "no RE" rule to allow it).
- Verdict: port must (i) use DHD masks `0x1F` / `0x3E0 >> 5` for SYS_MEM rev 9, (ii) bank index = `i + nrb`, (iii) NOT use bwfm's memtype-shifted `bankidx` unless verified (DHD writes plain `idx` for SYSMEM, a different register layout than SOCRAM) [src D/siutils.c:6969-6971 (SYSMEM: `bankidx = idx`) vs the SOCRAM variant D/siutils.c:7064-7068 which shifts the memtype in]. Reading RAM banks needs new `memw_ok` tuples (R40:162, U-N7).

### 1c. SRPWR request (PCIe core + 0x1E8) before SYS_MEM / ARM access
- bwfm never requests it (confirmed by the host run: HX:16). Not in `W/bwfm.c` or `W/if_bwfm_pci.c` for SYS_MEM/ARM access [src HX:16; handoff 39b says the same, super `docs/HANDOFF.md:47`].
- DHD: 4389 is `MULTIBP_CAP` [src G/g4389-include_siutils.h:963-968], attach sets `_multibp_enable = TRUE` [src G/g4389-siutils.c:2830-2832]. `_dhd_bus_pcie_pwr_req_cmn` requests domain 1 (`SRPWR_DMN1_ARMBPSD_MASK = 1<<1`) when MULTIBP_ENAB [src D/dhd_pcie.c:795-816 (read 795-815); D/include_sbchipc.h:5178-5183 (domain macros at 5178-5183)]. `si_srpwr_request(mask, val)`: shifts by `SRPWR_REQON_SHIFT 8` (so 0x2 -> 0x200), is a no-op when already set, otherwise write then read back, then spin-waits ExtPwrStatus `[19:16]` (`SRPWR_STATUS_SHIFT 16`, so bit 17 for domain 1) [src D/siutils.c:9311-9361 (read 9311-9340 and the tail); D/include_sbchipc.h:5199, 5202]. Register = `powerctl` at chipcregs offset 0x1E8 [src D/include_sbchipc.h:375; D/siutils.c:9280], reached on PCIe through the core alias `BAR0 + 0x2000 + 0x1E8` [src D/siutils.c:9285-9306; D/include_pcicfg.h:652]. In our window scheme the same register is reached via cfg 0x80 = 0x18001000 + BAR0 + 0x1E8 (PCIE2 core base `0x18001000`) [src R40:14 (PCIE2 base from EROM, obs n33); K/shim/wlanlink.c:211-212 (mem_ok win 0x18001000 off 0x1E8)].
- DHD calls it before the first `si_setcore(ARMCA7)` [src D/dhd_pcie.c:2203-2210].
- **Observed**: at S34 the register already read `0x00030300` (PowerOnRequest[11:8] = 3, ExtPwrStatus[19:16] = 3, PowerDomain id [31:28] = 0) in three separate runs [obs `L34` R34 row=1344/1348; `L35` and `L36` the same: `WLAN LINK R34 row=1344 rd=0x00030300`]. S34 was therefore skipped by the srp flag (no chip write) in `w3a-n35` and `w3a-n36` [src super `docs/HANDOFF.md:51-52`; K/shim/wlanlink.c:223 (memw_ok writes SRPWR only when id != 0 and `v == old|0x200`)]. And the later writes (SYS_MEM reset, CA7 halt) succeeded without any request being issued by us [obs `L36` summary `reached=S36 stopped=none restore=ok`, R35 row 1371 rd=0x1, R36 row 1407 rd=0x21].
- Verdict: the request is a NO-OP on the observed power-up state; the port should implement the DHD idempotent form (read powerctl, if bit 9 and bit 17 already set do nothing; otherwise set bit 9 and wait bit 17 up to PMU_MAX_TRANSITION_DLY, `D/include_sbchipc.h:4874-4876`) rather than omit it. Whether bit 9 is set by default after EVERY cold power-up, or only here, is **Unknown U1**; DHD's own request exists because other chips/states need it [guess]. The request stays within the existing `memw_ok` rule (only when id != 0 per review 16 finding 2, K/shim/wlanlink.c:223): with id = 0 as observed the existing guard REFUSES the write, so a port that needs the write on a different state must re-justify "id == 0" (U2).

### 1d. `cc_caps` (ChipCommon + 0x04) and pmucaps
- What bwfm does with it: reads `cc_caps` at `base+BWFM_CHIP_REG_CAPABILITIES (0x04)` [src W/bwfm.c:975-976; W/bwfmreg.h:29], and ONLY reads `pmucaps` (and thus `ch_pmurev`) if `cc_caps & 0x10000000` [src W/bwfm.c:981-986; W/bwfmreg.h:30]. `ch_pmurev` is used only by `bwfm_chip_sr_capable` (`< 17` -> 0) [src W/bwfm.c:1389], which is not on the firmware-download path.
- brcmfmac does the same gate [src B/brcmfmac-chip.c:1105-1108]; DHD the same (`CC_CAP_PMU 0x10000000u`, "PMU Present, rev >= 20") [src D/include_sbchipc.h:859; D/siutils.c:499]. DHD with AOB reads pmucaps from the separate PMU core (`PMU_CORE_ID`, +0x604) [src D/siutils.c:499-514].
- Required value: bit 28 (`0x10000000`) set. **Not observed**: `mem_ok` for window 0x18000000 allows only offsets 0, 0xAC, 0xFC, 0x1E0 [src K/shim/wlanlink.c:211-212]; CC+0x04 is not in any run (HX:17). R37 planned a log-only read of CC+0x04 [src R37:138] but it is not in the allowlist, so it never ran.
- What IS observed: PMU core (`0x18012000`) pmucapabilities low byte = `0x28` (rev 40) [obs w3a-n33, R40:14 "PMU rev 0x28"; R38:25, R38:33]; `capabilities_ext` = `0x000A044E`, AOB bit 0x40 set [obs `w3a-n31` R38:25; R37:158]. So the PMU data bwfm wants is readable directly from the PMU core without the gate.
- Proposed READ-ONLY check (not implemented): add the pair (window `0x18000000`, offset `0x04`) to `mem_ok` (and to the Python twin `_WLAN_MEM_OFFS`, K/tools/test-bluejay-boot.py:2836) and one `read_only` log row in an existing read-only step (S31 is the ChipCommon read step [src K/soc/google/gs101/wlan_seq.json steps "31"]); PASS = bit 28 set. Hardware-writing code is not touched (read allowlist only), but the table sha pin changes.
- Verdict: port reads `cc_caps` as bwfm does but must not ABORT or skip PMU access if bit 28 is clear; since pmurev is not used for download, the gate matters only for logging (U5).

## 3. XNU integration point (requirement 3)

### 3a. How a driver attaches today
- All XNU-side hardware drivers are plain files under `bsd/dev/sweet_*.c`, added by numbered patches (`0080-sweet-ufs-gs101` `bsd/dev/sweet_ufs.c`, `0082-sweet-usb-gs101` `bsd/dev/sweet_usb.c`, `0104-sweet-mali-driver-core` adds `bsd/dev/sweet_mali.c` to `bsd/conf/files` [src K/xnu/patches/0104-sweet-mali-driver-core.patch:1-12], etc.). The last patch is `0117-sweet-dev-overlay.patch` [obs `ls K/xnu/patches`]; contiguous numbering, `git apply`-clean [src K/xnu/AGENTS.md:6-7].
- They are called from the UFS root-device init, polled, single-slot: `sweet_ufs_init()` calls `sweet_keys_gs101_start()`, `sweet_touch_gs101_init()`, `sweet_gpu_gs101_init()` [src K/xnu/patches/0102-sweet-gpu-probe-xnu.patch:145-155]; USB is probed first from the same function [src K/xnu/patches/0091-sweet-usb-before-ufs.patch:5-20]. Rule: device-specific code gated on the ADT `compatible`, drivers polled and single-slot, DMA buffers physically contiguous and cache-maintained [src K/xnu/AGENTS.md:9-13].
- ADT lookup pattern (the template for a Wi-Fi driver): `SecureDTLookupEntry(NULL, "/sweet-usb", &node)`, `SecureDTGetProperty(node, "compatible"/"reg")`, `ml_io_map(reg[0], reg[1])` [src K/xnu/patches/0082-sweet-usb-gs101.patch:150-161]. The node is written by `tools/mkadt.py` from `soc.json`/`board.json` only for boards that name the core [src K/tools/mkadt.py:249-257].
- An ADT `wlan` node already exists, but only as a flag: `node('wlan', [..., ('device_type','wlan'), ('compatible','sweet,wlan')])` under `arm-io` when `wlan_node=True`; it makes launchd start wifid and carries no `reg` [src K/tools/mkadt.py:208-210; K/tools/test_mkadt_wlan.py:26-28]. wifid/IOWiFi glue is a separate checklist: R26 and flame notes [src FB:129-130 list].

### 3c. Where the firmware bytes come from
- Extracted on the host from the user's own factory `vendor.img`: `fw_bcmdhd.bin` 1,764,018 B, `bcmdhd.cal` 27,062 B, `bcmdhd_clm.blob` 15,932 B, under `~/pixelios-artifacts/wlan-fw/files/`, never in git [src R39:s.1 table and "Not copied"].
- Delivery design (recommended A): one container with magic `WLANFWB1` (tag, length, offset 8-aligned, CRC32), built by a host script and used as the boot ramdisk (`ramdisk.bin`); the shim finds it by scanning `[linux,initrd-start, linux,initrd-end)` from /chosen [src R39:35-43 (design), K/shim/loader.c:75-82, K/shim/payload.c:3-15 (magic scan)]. An xnu payload already travels this way: `SWEETXNU` is found in the same initrd range and COPIED into XNU memory [src K/shim/loader.c:75-100]. The ABL initrd is NOT copied for XNU: `loader_boot` refuses an initrd that overlaps `[phys_base, phys_base+mem_size)` [src K/shim/loader.c:94-96], so the ramdisk stays at its ABL address outside XNU's memory, and `boot_args`/ADT carry no initrd range [src K/shim/loader.c:112-135 (boot_args fields: no initrd member set)].
- Therefore XNU cannot find the container unless the shim tells it: the missing link is an ADT property (physical address + length + CRC32 of the `WLANFWB1` container), written by the shim when it patches the ADT, or a boot-arg. Neither exists as a shim-written property. Route A' exists today for a blob embedded in the XNU payload: `tools/mkpayload.py:20-26,125-131` (`--ramdisk`) appends it after the kernel (inside topOfKernelData, never handed to the VM) and writes `/chosen/memory-map` `RAMDisk = <phys,size>`, which patch 0117 already reads (`xnu/patches/0117-sweet-dev-overlay.patch:71,91`) [src]; but there is one `RAMDisk` property (`mkpayload.py:130` asserts none exists), so WLANFWB1 and the dev overlay collide unless one container carries both. Route A (ABL initrd + new ADT property) does not exist. **Unknown U10: choose A or A'.** Also unknown: whether XNU's pmap treats that physical range as RAM it may later hand out (the USB pool precedent maps an ABL "reserved range" through `ml_io_map_wcomb` [src K/xnu/patches/0082-sweet-usb-gs101.patch:222-228]); the range must be mapped read-only with `ml_io_map` and never added to the free list (U11).
- Placement into the chip (from R37 s.4 / R39 s.8 step 7): image copied to `dongle_ram_base` (0x200000, 1a); NVRAM at `ram_end - 4 - roundup4(varsz)` with the length token at `ram_end - 4`; RNG rTLV below the vars; CLM only after the firmware runs [src R39:72 (UD) and 88-89 (step 7 text)]. The 32 KiB NVRAM cap and `process_nvram_vars` semantics are in R39 s.4. The `ram_end` depends on ramsize (U3/U4).

### 4a. Existing, audited facts the guard can adopt (centralised properties)
The shim already has the pattern: a single write path `w32` that must call `w32_allowed(pa, mask, old, v, ctx)` BEFORE writing, audited at source and object level, with mutants [src K/shim/wlanlink.c:355-440 (`w32_allowed`, call at 439); K/tools/test-bluejay-boot.py:1365-1422 (`check_usbgadget_source_text`: no asm, no integer-literal pointer casts, `w32` guard before the write, allowlist depends on the address); 1456-1477 (strict/touch variant and mutants); 3802-4158 (`check_wlanlink_source_text` + 10+ mutants)]. The table twin (Python) checks every write row against the same sets [src K/tools/test-bluejay-boot.py:2828-2864].

Window registers (property: "window moves only along an audited chain, restore on teardown", centralised):
- cfg 0x80 (`PCI_BAR0_WIN`, backplane address mapped at BAR0) [src D/include_pcicfg.h:488]. Forward chain: 0x18000000 -> 0x18105000 (EROM) -> 0x18012000 (PMU) -> 0x18120000 (CA7 wrapper) -> 0x18126000 (SYS_MEM wrapper) -> 0x18001000 (PCIe core) -> 0x18126000 -> 0x18026000 (SYS_MEM core) -> 0x18120000; each step only from its predecessor, only while Command = MEM-only and BAR0 low = the S28 assignment; teardown restores 0x18001000 (the observed original) from any state [src K/shim/wlanlink.c:330-349; K/tools/test-bluejay-boot.py:2835 `_WLAN_S34_WINDOWS`].
- cfg 0x84 (`PCI_BAR1_WIN`, window for the second BAR) [src D/include_pcicfg.h:489]: observed 0, never written; NOT in the allowlist (`cfg_ok` returns 0 for it). The TCM download needs it (1a) only if RAM crosses 4 MiB-aligned windows.
- cfg 0x70 (`PCIE2_BAR0_WIN2`, wrapper window "2nd 4 KB of BAR0") [src D/include_pcicfg.h:633; R36:10]: observed 0x18101000, never written; not allowlisted. bwfm never uses it: it writes cfg 0x80 with `page = reg & ~0xFFF` before EVERY register access and reads cfg 0x80 back in `select_core` [src W/if_bwfm_pci.c:1058-1060, 1805-1820, 1826-1842; `BWFM_PCI_BAR0_WINDOW 0x80`, `BWFM_PCI_BAR0_REG_SIZE 0x1000` W/if_bwfm_pci.h:20-21]. So the port's single choke point is `bwfm_pci_buscore_read/write` + `select_core`; the guard must wrap the cfg 0x80 write there (HX:18).

DENY list (proposed for the XNU guard; the shim enforces the equivalent today):
- UFS HCI (`ufs_base 0x14700000`) and any UFS DMA/command path: no WRITE through the Wi-Fi port; AGENTS "Do not add a UFS write path to the shim" (the XNU UFS driver is a separate, existing driver that writes userdata) [src K/soc/google/gs101/soc.json:11; AGENTS.md "Do not"].
- PMIC / ACPM: no S2MPG10 or ACPM write from the Wi-Fi port. WLAN rails are read-only today (`wlanrails.c` is an audited READ-ONLY client of S2MPG10 LDOs 0x53-0x56) [src K/tools/test-bluejay-boot.py:2179; K/soc/google/gs101/soc.json:196 text (`s10_l16m..l19m_ctrl` read by `--wlan-rails`)]. If the port ever needs a rail ON, that is a NEW write needing its own cited sequence (U13).
- OTP/fuse: no access (CC OTP is not in any allowlist; neither CC OTP registers nor the PMU OTP regs appear in `mem_ok`) [src K/shim/wlanlink.c:204-216 (exhaustive list)].
- PMU (`0x17460000`): only the PCIe1 PHY isolation word `0x17463EC4` through the audited EL3 SMC RMW, 2 values; and the PMU txco word is read-only [src K/tools/test-bluejay-boot.py:2459-2461, 2548-2575; K/soc/google/gs101/soc.json:21, 34].
- Any other BAR0 window, any BAR0 offset not in `mem_ok`/`memw_ok`, MASTER (Command bit 2), BAR2/BAR4 TCM writes and ATU region 2+ are denied today [src K/shim/wlanlink.c:199-236, 330-333]. The port needs a controlled expansion for BAR2 (TCM download) and bus mastering (msgbuf DMA); those are NEW and are not covered (see 4c).

### 4b. Properties the guard may enforce centrally (user decision 2, FB:234)
1. A write goes only through one function; no asm, no pointer casts (source audit, K/tools/test-bluejay-boot.py:1365-1422).
2. Address ranges (the ALLOW table's blocks and sizes) and word alignment.
3. Enforcement of per-register write masks and exact value sets (deciding them is device-specific, see 4c) (ATU, ELBI offsets, GPIO field masks, CFG transitions).
4. Window-chain ordering and "restore on teardown" (cfg 0x80, ATU disable first, Command 0), plus "region 1 ENABLE last".
5. Bounded polls (the shim has them, `wlanlink.c:8,450`) and per-rule dead-read checks (`wlanlink.c:224,234,349,388-394,505-507`); a general refuse-and-restore on any all-ones read is PROPOSED, not existing.
6. Predecessor-state rules (e.g. RESET_CTL release only after the IOCTL write; bankidx only with nrb = 0) are enforced as code in `memw_ok`, but their CORRECTNESS is a porting assumption (4c).

### 4c. Properties the guard does NOT cover; each needs a per-step cited source or measured result (rule 7)
- The meaning of every chip register and the sequence order: SRPWR (1c), core reset order and values (CA7 0x23 -> 0x21, SYS_MEM 0x3 -> 0x1 [src K/shim/wlanlink.c:222-228, R40 s.5; obs L36]), CPUHALT = 0x20 (DHD `SICF_CPUHALT` [src G/g4389-include_siutils.h:306]).
- Bank decode (1b), RAM base/size (1a), NVRAM placement, the rTLV layout (R39 s.5).
- Timing: 10 us bank settle, SRPWR spin (DHD `PMU_MAX_TRANSITION_DLY`, 15 ms or 1.5 s by build, `D/include_sbchipc.h:4874-4876`, spin at `D/siutils.c:9428-9430`), delays after PERST (cite per delay).
- State at hand-off between the shim and XNU: power-up state of powerctl (1c), whether the link is up when XNU starts, the BAR/ATU/window values (U8).
- Which rail/clock state XNU inherits (S5-S19 effects) if the shim stops after S30.
- Bus-master DMA: Command MASTER is refused by the shim today; DHD msgbuf DMA to host memory needs it, plus the PCIe1 IOMMU/S2MPU configuration. No source has been opened for that here (U14).
- The firmware's own behaviour after ARM release (shared-area discovery, R37 s.7).

- The contents of every ALLOW entry (values, masks, offsets) need their own source or measurement; the guard only enforces them (review 20 F7).
