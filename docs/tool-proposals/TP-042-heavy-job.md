## memory gate (first-class check, W23 2026-10-28)
Finding: up to 10 agent sessions at once, several with 6-9 GB memory peaks this boot, plus one XNU build (-j4), a qemu VM build (512 MB guest + host image I/O) and a phone run, on a 31 GB / 16-core host with 23 GB swap that also runs docker/buildkitd/Sonarr. Most likely cause: memory, not CPU. Root dump pending to confirm. So every `run` checks memory first, before taking the lock and again just before it starts the job. It refuses to start unless MemAvailable >= the class need (`--mem-gb`; defaults to measure: build 8, vm 4, mutant 4, gate 8, analysis 4) + a fixed host reserve (8 GB for agents/services) and PSI memory `some avg10` < 10. It also reports load1 (W23 interim rule: local start only when load1 < 6 and MemAvailable > 12 GB). The result line always carries `mem_avail=`, `psi=` and `load1=`. Waiting is bounded by `--wait` and the tool says why it waits; on timeout it exits 2 with `RESULT: ERROR memory-gate ...`. Agents are not throttled: the gate only delays new heavy jobs.

## output
One tool, two verbs, agent friendly.
- `run`: (1) **resubmit check first** (user, 2026-10-28 via W23): on the chosen host, if a result dir/log for the same `--label` exists that was never collected, or a container/process for that label still runs (`docker ps --filter label=pixos.job=NAME`, the remote-job pid file), print it (path, rc, age, container id) and refuse with `RESULT: ERROR resubmit label=NAME has result|orphan ...` exit 2; `--collect` fetches/acknowledges it, `--kill-orphan` stops it. (2) **placement**: `--prefer <offload-host>` (default for build/mutant/analysis/gate classes, user 2026-10-28 via W23) uses <offload-host> (<host-ip>) through tools/remote-job when <offload-host> is reachable and its `docker ps` shows no pixos job and its heavy-job lock is free; else local; `--prefer local` for jobs that need the phone or local artifacts. (3) **one heavy-job lock per machine**: `flock` on a fixed path outside /tmp (`~/.cache/pixelios/heavy-job.lock`, holder label+pid+class+start written into it) taken by every heavy class; check-all.sh, xnu-local-build, gate-xnu-build, rootless vm.sh build, mutant suites and rea analysis call it (or are wrapped by it). (4) **load gate** before start and while waiting: MemAvailable >= `--mem-gb` (class default, e.g. build 8, vm 2) and no swap-in storm (PSI `/proc/pressure/memory` some avg10 < threshold); otherwise wait (bounded by `--wait`, default 1800 s) and say why. It never renices, cgroups or throttles running services (global rule); it only decides when a new heavy job starts.
- `status`: holders and waiters on local and <offload-host>, uncollected results, orphan containers.
Report: one line per decision (`host=<offload-host> lock=acquired mem_avail=19G psi=0.4`), last line `RESULT: PASS|FAIL|ERROR ...` = the wrapped job's result; exit 0/1/2; log in the MAIN clone's `logs/heavy-job/<label>/` (parent of `git rev-parse --git-common-dir`; AP-217, so removing a worktree keeps the log), path printed before RESULT.

## risks
No device, no root, no flashing. xrun/phone runs are not heavy-job classes (phone-lock already serialises them) but count toward the load gate. Must never kill another owner's job (only `--kill-orphan` on an orphan of the same label, with the holder pid proven dead). Lock path must survive across sessions but not across reboots in a held state (flock is released by the kernel on crash; stale holder text is informational only). Tools owned by driver 20 (xrun, gates, check-all, remote-job) are changed only by driver 20.

- 2026-10-28 Claude Opus 5.5 (driver 20c): <OFFLOAD-HOST> QUEUE (user request via chat 2026-10-28 ~23:20 CET: "a <offload-host> gate queue like tools/phone-lock"). Folded in here, not a new TP, because TP-042 already owns the <offload-host> lock (`remote-job` `.heavy.lock`, rc 97), `status --host <offload-host>` and the resubmit check. What the user's rule needs that a1032d63/6924215 do not give: (1) a FIFO across submitters on this host (flock wake-up order is unspecified, so "waiting" jobs can overtake each other), (2) admission on <offload-host> state, not only "lock free": load1 < 8 AND MemAvailable > 12 GB AND no foreign heavy job (the second T3 instance on <offload-host> runs vitest/node in <data-mount>/mymacro-work [obs 22:59]; its load already counts in load1, and a running foreign vitest/claude-build process blocks admission on its own), (3) owner/label visible to every agent, (4) no bypass: `remote-job` takes the slot itself.
  Usage: `tools/heavy-job <offload-host> run --owner NAME --label NAME [--wait SEC] -- CMD...`, `tools/heavy-job <offload-host> status`, `tools/heavy-job <offload-host> wait [--wait SEC]` (returns when the queue is empty or the caller's turn comes). `tools/remote-job` re-execs itself under `heavy-job <offload-host> run` for every route that may reach <offload-host> (`--where auto|<offload-host>`), marker env `OFFLOAD_QUEUE_HELD=<label>` (a nested call does not queue twice; a `--where local` run does not queue; `--collect` and `--kill-orphan` never queue, they take no CPU and the orphan container they kill is what makes admission refuse; `--where auto` decides once before the queue: <offload-host> unavailable there means `--where local`; the gate-pre XNU pre-check runs before the queue).
  FIFO: queue dir `${OFFLOAD_QUEUE_DIR:-$HOME/.cache/pixelios/offload-queue}`; a ticket = monotonic number taken under one flock + file `NNNNNN.<label>` (owner, label, pid, start); each waiter holds a flock on its own ticket for its lifetime and blocks (`flock`, no sleep) on the ticket before it, so the turn passes in order and a dead waiter's flock is freed by the kernel (stale tickets whose pid is dead are removed by the next taker). Head of queue = admission phase.
  Admission (head only): one ssh probe `ssh -o BatchMode=yes -o ConnectTimeout=3 <host-ip> 'cat /proc/loadavg; grep MemAvailable /proc/meminfo; pgrep -af ...; ls <work-dir>/jobs/.heavy.lock holder; docker ps --filter name=rj-'`. Admit iff load1 < OFFLOAD_MAXLOAD1 (8), MemAvailable > OFFLOAD_MINAVAIL_GB (12), no rj- container running, no foreign heavy process (pattern list OFFLOAD_FOREIGN_RE, default `vitest|<data-mount>/mymacro-work.*(node|tsc|esbuild)`). Not admitted: one line with the reason each re-probe; re-probe interval 60 s (remote state cannot notify us; this is the only timed wait and it is inside the tool, never in an agent), give up after --wait (default 7200) with `RESULT: ERROR offload-queue ...` exit 2. the probe ssh is wrapped in `timeout ${OFFLOAD_PROBE_TIMEOUT:-30}`: a timeout is a loud `probe error` line and is retried like a refusal (never an admission); a failing/missing `docker ps` or a missing `rj=` answer is a probe error (`RESULT: ERROR <offload-host> unreachable (docker check failed ...)`), never read as "no rj- container"; an existing but empty `.seq` is `RESULT: ERROR` (no silent renumbering). Other ssh failure = `RESULT: ERROR <offload-host> unreachable` (remote-job's own auto fallback stays as it is).
  Output: `status` = holder (owner/label/pid/age), waiters in order, last probe; every verb ends in `RESULT: PASS|FAIL|ERROR`, exit 0/1/2; `run` keeps CMD's rc (0 PASS, 1 FAIL, 2 ERROR). Log logs/heavy-job/<offload-host>/<label>.log. Host test with a fake ssh (probe answers from files), concurrent waiters proving FIFO order and dead-waiter removal, no network; shellcheck.
