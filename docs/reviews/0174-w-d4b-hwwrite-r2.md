## New findings

### F10 MEDIUM (test gap on a restore path): nothing pins "the F9 check never blocks 0xC34 := 0"; a mutant that blocks the unmask survives
- Where: G:396 / P:184 `... && off == 0xC34u && v != 0u && sw3_g2_irq_off(h, v) != 0`; harness T:2135-2163 has no 0xC34 := 0 case at all, and g2irq() sets an enable only for cases named "mask with RC irq*" (T:2177), which all expect -1.
- Shown [obs, this review, T run_glue on the applied glue, base sweep PASS]: mutant `v != 0u && ` removed (the check also on the 0xC34 := 0 restore) -> sweep PASS (SURVIVED). Mutant "win == SWW_WIN_PCIE && removed" -> PASS too (behaviourally equivalent: a BAR0 0xC34 store in another window has no list entry and is refused anyway; mark it EQUIVALENT or leave the clause).
- Failure scenario: a later edit that drops `v != 0u` (or checks the enables in the unmask too) passes every test. On hardware, if an RC enable gets set between the mask store and the undo (or reads nonzero), the unmask 0xC34 := 0 is refused, so the 16 mailbox bits stay unmasked after G2: the exact state F9 exists to avoid, now permanent instead of <= 2 s.
- Fix: in GLUE_HARNESS gc (after the "mask" row T:2157) add `{ SWW_BAR0, SWW_WIN_PCIE, 0xC34u, 0u, 0xFFFFu, 1, 10, 1, 2, <unmask entry index>, "unmask with RC irq1 enable set (never blocked)", 2u }` and make g2irq() set irq1_en for names starting "unmask with RC irq"; add to GLUE_MUTANTS `("F9: the check blocks the unmask", [("&& off == 0xC34u && v != 0u && sw3_g2_irq_off(h, v) != 0)", "&& off == 0xC34u && sw3_g2_irq_off(h, v) != 0)")])`.

### F11 LOW (rule 8, false alarm): a refused mask store still triggers the unmask, which the glue refuses, and the run prints "0xC34 restore FAILED, interrupts may stay masked" and undo=FAILED
- Where: header g2:1048 `x->d4tried |= 1u << r;` before swg_put; swg_d4_unmask g2:398 keys on d4tried (attempted); glue unmask entry G:702 has `need = m` (the mask entry must be done).
- Failure scenario [src chain]: F9 refuses the mask (an enable set) -> swg_put != 0 -> swg_stop -> swg_undo -> swg_d4_unmask attempts 0xC34 := 0 -> sw3_g2_ok finds no entry (need not done) -> "glue: store not in the G2 list, refused" [high] + "G2 STOP: d4b mask 0xC34 := 0 FAILED (read back 0xffffffff), interrupts may stay masked" + `G2 RESULT STOPPED ... undo=FAILED`. 0xC34 was never written. The same happens for a mask refused by the link check. H:1333 (`nunm == mask_stored`, "stored iff attempted") pins the header side of this mismatch, so the fake bus never shows it. Not unsafe, but the run summary claims an unrestored hardware state that does not exist, and F9 makes this the predicted path when an enable is set.
- Fix (same contract as SWT_ARMST, which the glue honours: nonzero = nothing stored, G:395-437, sw_g2_wr G:899-900): in swg_d4_row set the MASK attempt bit only after a store that returned 0: move `x->d4tried |= 1u << r;` below `if (swg_put(...)) return swg_stop(...)` for r == SWG_D4_MASK (keep it before for the others, or for all rows if no other reader needs the attempt). Update H:1333's stop table so a refused mask expects no unmask and no FAILED line; add a G2 mutant "d4b: mask attempt bit set before the store" that the new case kills.

### F12 LOW: the C88 restore does not depend on the CA7 re-halt having held
- Where: swl_restore wr:906-960: a CFG row after SWF_W16 is skipped only for precondition 1..4 or 8; the CA row (BAR0) is skipped for any nonzero precondition, and a failed CA store sets bad and continues.
- Failure scenario [src + guess]: CA re-halt skipped (precondition 5/6/7) or FAILED (ca_ok 0) -> C88 is still stored, so cfg 0x88 goes 0x80380 -> 0x80080 while firmware runs. DHD never clears these bits under a running CA7 (it sets them at attach, dhd_pcie.c:2224-2229, and does not restore them); the effect on a running dongle is not documented [guess: BAR1/BAR2 coherency only, r1 point 4]. The comment "restored after the CA7 re-halt" (wr:316, wr:444) is then not true. Loud already (W17 STOP CA7 re-halt not confirmed), so LOW.
- Fix: in swl_restore, before the C88 store: `if (r->grp == SWW_RG_C88 && (x->flags & SWF_W16) && !x->ca_ok) { swl_gap("restore", "cfg 0x88 restore skipped: CA7 not re-halted", "high"); skipped = 1; continue; }` (leaving the DHD state with a running CA7). Host case: CA restore FAILED -> no 0x88 store, SKIPPED; mutant drops the condition.

## New antipattern (reported here; the reviewer is read-only outside this file)
- "Guard added on a shared store path with a value condition (`v != 0`) but only the refused side is tested": the side the condition exists to protect (the restore, which must never be blocked) had no case, so dropping the condition survives. Every value-conditional guard needs one case per side.
- Repeat of r1's "armed from intent" in a second place: the header keys the unmask on the mask attempt while the glue keys it on the mask store (F11). When two layers both decide "was it stored", they must use the same truth.
