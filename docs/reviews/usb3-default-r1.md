## Findings

### F1 (MEDIUM) tools/usb-port:9-10,34-35 and tools/xrun:81-89: sweetusb3 != 1 on a >= 5000 link was a refusal, now a PASS with a WARN
- Before (0676d2a): speed >= 5000 and no `sweetusb3=1` -> `RESULT: ERROR`, exit 2 (AP-177: "0 B USB log, no software reset, phone hung absent, Power+VolDown, re-flash needed", ba6-cpucap boot1 [obs-hw]). Now the same run (explicit `sweetusb3=0`, or `=2`, `=10`, empty) passes preflight with `USB3 WARN` and the mark ` sweetusb3=0 OPT-OUT` in the summary, then builds, locks the phone and runs.
- Failing scenario: an agent copies an old plan line with `sweetusb3=0` (or a typo `sweetusb3=2`, which C treats as SS off) onto the user's USB 3 port; xrun proceeds, the phone gets a gadget that gives 0 B, a hung phone needs the human (Power+VolDown). Loud is not the same as prevented; the old guard existed for exactly this.
- Fix: keep the refusal for the opt-out on a >= 5000 link unless explicitly bypassed. In tools/usb-port: when `mbps >= 5000 && usb3 = 0` print the WARN and `echo "RESULT: ERROR usbport $bus speed=$speed sweetusb3=$optout is an opt-out on a USB 3 link (AP-177: 0 B of USB log)"; exit 2`, honoured only without an env `USBPORT_ALLOW_OPTOUT="reason >= 10 chars"` (then PASS + the WARN + `OPT-OUT BYPASS` in the RESULT line so xrun's mark shows it). Update test_usb_port.py cases `sweetusb3=0|10|1x` accordingly (rc 2, and rc 0 with the env). If the user's R27 text means "opt-out must stay usable on USB 3", record that decision in docs/HANDOFF.md and keep the WARN; the choice is the driver's, but the default must not be silent about the regression.

### F2 (LOW-MEDIUM, rule 8) xnu/patches/0173-sweet-usb3-ss.patch:344 and :366-371: the default-ON line is printed before the gadget is known to start; the default has no "not started" GAP
- sweet_usb_probe_gs101 prints `SWEET USB3: default ON` (patch :344) before the DMA-pool checks and before sweet_usb_gadget_start. Paths after it that do not reach `ud.hw_started = true`: probe_gs101 `no dma-pool-range` / `GEVNTADR ... no DMA pool` (these print their own line), `SWEET USB: no DMA memory` (own line), and `if (!pn) { return; }` in sweet_usb_gadget_start (silent, pre-existing). For an explicit `sweetusb3=1` the final `USB3 GAP: sweetusb3=1 ignored: gadget not started` fires (patch :369-371); for the default it is now deliberately silent, so on the `!pn` path the log shows "default ON" and then nothing: a stub that looks like success.
- Fix: add a `bool ss_req` file-scope or `ud.ss_req` set at the point where `SWEET USB3: default ON` / `sweetusb3=1: SuperSpeed requested` prints, and change the final guard to `if ((usb3_explicit && usb3 != 0) || ud.ss_req) && !ud.hw_started`. The default on non-gs101 / sweetusb=0/1 stays silent (ss_req is only set in the gs101, mode >= 2 branch). Add the matching assert in test_usb3_desc.py (test_f9_*).

### F3 (MEDIUM, rule 5/7) xnu/patches/0173-sweet-usb3-ss.patch:14 and the default-on claim: the default path itself, and the HS fallback, have no hardware result
- "Not observed on hardware yet." (patch :14) is now wrong in both directions: explicit `sweetusb3=1` is [obs-hw] (usb3-ss-1 HS connect on a USB 2 link, usb3-ss-2 SS on a USB 3 port), the default-ON build is not. The 10000 ms HS restart (`ud_restart`, sweet_usb.c 1426-1470; `ud_ss_fallback` 1476-1488) never fired in either run (usb3-ss-1 row 3 "no fallback"), so it is [read]/[host-text-assert] only, yet it is now on the path of every run whose link does not come up at SuperSpeed (old USB 2-only cable in a USB 3 port, hub, other host controller). Also only ECM log traffic was run at SS; usbroot (0172 rxfast, bulk 1024 packets) over SuperSpeed has no run in docs/runplans/usb3-ss.md [read].
- Fix: (a) patch header line 14 -> "Explicit sweetusb3=1 observed: usb3-ss-1 (USB 2, HS, no fallback), usb3-ss-2 (USB 3, SS). Default-ON build, the HS fallback and usbroot over SS: not observed on hardware yet." (b) the first run of this build (xrun label, run plan with `--expect` rows) must list: default on a USB 2 port -> `SWEET USB3: default ON` + `connected at high speed` + absent `USB3 GAP: not configured`; default on the USB 3 port -> `connected at SuperSpeed 5 Gb/s`; and one deliberate `sweetusb3=0` on the USB 2 port. Until then the claim "SS default works" is [guess] for the default build. Do not call the default "proven" in HANDOFF.

### F4 (LOW) tools/usb-port:33: string compare against `sweetusb3=1` disagrees with XNU's numeric parser on `=01`, `=0x1`, `=1k`-style spellings
- `sweetusb3=01` is octal 1 and `sweetusb3=0x1` is hex 1 in getval (bootargs.c:424-440), so XNU runs SuperSpeed; usb-port classifies both as opt-out (usb3=0, "USB3 WARN: ... opt-out ... HS-only", xrun mark `sweetusb3=0 OPT-OUT`). Direction is harmless (false warning, and with F1 fixed a false refusal on a USB 3 link that would have worked), but the mirror is wrong. New antipattern AP-268 added.
- Fix: in usb-port treat a value `V` as: `1` -> on, `0` -> off, anything else -> print `USB3 WARN: sweetusb3=V is not a canonical 0|1: XNU parses it numerically (01 and 0x1 mean 1, other numbers are 'unsupported', SuperSpeed off); use sweetusb3=0 or =1` and, with F1, exit 2 on a >= 5000 link. Add a test with `sweetusb3=01` and `sweetusb3=0x1`.

### F5 (LOW) tools/usb-port: the effective value ignores the bare word `sweetusb3` and `sweetusb3=` exactly as C does, but `sweetusb3=0 sweetusb3` (bare after an opt-out)
- C: the bare word re-sets usb3 to 1 (bootargs.c:483-484), so SS is ON; usb-port keeps the earlier `=0` (the bare word does not match `sweetusb3=*`). False OPT-OUT report again (harmless direction). Same fix as F4 (also treat a bare `sweetusb3` word as `=1`) or have xrun reject bare/duplicate sweetusb3 words in `--args` with one line.

### F6 (LOW-MEDIUM) tools/probe-run:104-114 + header :12-14: the preflight refuses every probe-run on a >= 5000 link on trunk today, with no override, and its two test hooks are silent
- shim/build.sh on trunk has no `--usb2` (grep on this worktree: no match), so the proxy `grep -q -- '--usb2' "$BUILDSRC"` is false and EVERY probe-run (all kinds, including udump / touch / wlan-link runs) on a 5000 link now ends `RESULT: ERROR ... (exit 2)` before the build. That is the stated intent (HS-only shim gadget gives no log on the SS port: pr3-ctl-1, HANDOFF line 1245 [read]) and the self-test covers it (usb3-hs-only-shim). Concerns: (a) a normal probe-run on a USB 2 link is unchanged except for one extra host-only call and one new failure mode: if two 18d1 devices are on the bus or the speed is unreadable, `usb-port` exits 2 with something other than "0 Google" and probe-run now reports `ERROR USB port check failed` (before: ran); (b) the proxy is "the text `--usb2` occurs anywhere in shim/build.sh": a comment or a usage line mentioning `--usb2` before the SS-by-default gadget lands would lift the guard; (c) `PR_USBPORT` and `PR_BUILDSRC` replace the safety check silently when exported (every other PR_* hook has the same property, but these two disable a hang guard rather than a tool path).
- Fix: (b) grep for the real option parse, e.g. `grep -q -- '^[[:space:]]*--usb2)' "$BUILDSRC"`; (c) after resolving the hooks add `[ -z "${PR_USBPORT:-}${PR_BUILDSRC:-}" ] || echo "PROBE-RUN TEST HOOK: PR_USBPORT/PR_BUILDSRC set, USB port preflight is NOT the real one" >&2`, and make the self-test export them only inside `chk`; (a) document in the header that a second Google device now refuses the run (it is desirable under AGENTS rule 2, just say so). A one-shot bypass is not required if F1's decision is "refuse": the user can use a USB 2 port, as the message says.

### F7 (LOW) tools/xrun:7,81-89: the USB3 WARN for "SuperSpeed requested on a USB 2 link" is printed for runs that have no gadget
- usb-port assumes SS-requested whenever the speed is < 5000 and no `sweetusb3=0` word, but `--no-usbnet` (build-xnu-image.sh:40-41 keeps `sweetusb=0`) or an explicit `sweetusb=0|1` in `--args` start no gadget, so the WARN and the summary mark ` USB3 WARN (SuperSpeed requested on a USB 2 link)` are false for those runs; on a USB 3 link the same runs get the opposite (no SS "requested" but no gadget either). Rule 8 cuts both ways: a warning that is always printed is ignored.
- Fix: pass whether a gadget is requested into usb-port (`--args` already holds `sweetusb=N` only when the user typed it; xrun knows `$usbnet`): in xrun call `tools/usb-port --args "$args${usbnet:+ sweetusb=2}"`, and in usb-port evaluate the SS state only when the last `sweetusb=` word is 2 (otherwise print `usb-port: ... sweetusb3 n/a (no gadget)`). Test both.
