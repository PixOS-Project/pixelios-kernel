# Review: T-c170 commit 4ca3e882 (xnu patch 0191 `sweethang=1`, tools/bootargs-known.txt)

Reviewer: Opus 5.5, HW-WRITE adversarial review, 2026-11-01. Read-only; nothing but this file was written (plus a scratch
copy `~/pixelios-artifacts/scratch/c170-review-copy` of stack-YjwRSe with 0191 applied; the original tree is untouched).
Line numbers `T:` = that patched copy (stack through 0185 + 0191); `W:` = the T-c170 worktree.

## Verdict: SAFE WITH CONDITIONS

The patch itself adds no MMIO, SMC or storage write, is off when the arg is absent, and sits at the right point. The only
hardware write in this run is the existing 0083 PMU reset. The conditions are about the run failing for the wrong reason,
which would leave the phone spinning with no USB until someone holds Power+VolDown: F1 and F2 (interlocks in the patch,
or at minimum the planned command must keep `--qr N` and `--cpus 8`), and F3 and F4 (run-plan evidence).

## Findings

1. **Medium: patch, no-poller interlock (W:xnu/patches/0191:18-27 → T:sweet_ufs.c:67-82).** The hang runs before the only
   default poller starts (T:sweet_ufs.c:760). Without `sweetqr=N`, nothing ever calls `sweet_restart_poll`, so
   `sweetrestart` never fires and the phone stays off the bus until someone holds Power+VolDown.
   - The host check does not catch this: W:tools/run-preflight:547-556 (`c_recovery`, T-322d) passes on `--restart` alone,
     so `--args sweethang=1` without `--qr` passes preflight. The planned command has `--qr 1500`, so this run is OK only
     because of how the command was typed.
   - Fix (in 0191, so the hook refuses instead of hanging unrecoverably). Before the `SWEET HANG:` printf add:
     ```c
     uint32_t qr = 0;
     extern int sweet_restart_armed(void);   /* new 3-line accessor in bsd/dev/sweet_restart.c: return sweet_restart_deadline != 0; */
     if (!PE_parse_boot_argn("sweetqr", &qr, sizeof(qr)) || qr == 0 || !sweet_restart_armed()) {
         printf("SWEET HANG GAP: sweethang=1 refused: sweetqr=%u armed=%d, no thread would fire sweetrestart (sweet_qr.c:264), not hanging\n", qr, sweet_restart_armed());
         return;
     }
     ```
     Add the accessor as a second hunk of 0191 against bsd/dev/sweet_restart.c.
   - Separately, outside this commit: `c_recovery` should also require `--qr S>0` (or `sweetqr=`). If it does not, its PASS
     detail should say "covers hangs after UFS init (log thread, sweet_ufs.c:760) only, unless --qr". As written, the T-322d
     check passes exactly the before-UFS hang it was built for.
     AP-CANDIDATE: a self-reset check that tests that the timer is armed but not that a poller will run [src
     run-preflight:555, sweet_ufs.c:760] | guard: run-preflight:c_recovery require --qr when no poller precedes the hang
     point.

2. **Medium: patch, boot-CPU monopolisation (0191:25-27).** The spin is a fixed-priority-95 thread bound to the boot CPU, so
   the QR thread (BASEPRI_KERNEL, T:osfmk/kern/thread.c:1527, 1960) can only run on a secondary CPU.
   - Secondaries are started asynchronously by `cpu_boot_thread`, itself a priority-81 kernel thread
     (T:iokit/Kernel/arm/AppleARMSMP.cpp:158-237, started at :252-255). Nothing on the bsd_init path waits for
     gIOAllCPUInitializedKey before IOFindBSDRoot.
   - With `--cpus 1` (a legal xrun value, W:tools/xrun:80 el2), or if `cpu_boot_thread` is late, the QR thread and
     `cpu_boot_thread` both starve. The test then fails, and the plan's "If wrong" branch (Q2, "timer is not independent of
     boot progress") would draw the wrong conclusion.
   - Observed: in 25 logged runs (logs/runs/*/usbnet.log, `grep -a`), `SWEET CPU: 8/8 CPUs initialized` comes before
     `SWEET USB: DWC3 GSNPSID`. In 20261029T153448Z-iortc-1 the lines are interleaved, but the timestamps give
     340.568 < 340.614, a margin of only ~46 ms. So the run works by an observed ordering, not by construction.
   - Fix (in 0191, before the spin):
     ```c
     extern uint32_t processor_avail_count;           /* osfmk/kern/processor.c:138, ++ in processor_up osfmk/kern/machine.c:142 */
     unsigned want = ml_get_cpu_count();              /* cpus= cap, fixed before any CPU starts (sweet_el2.c:46-47) */
     for (int i = 0; i < 100 && os_atomic_load(&processor_avail_count, relaxed) < want; i++) delay(100 * 1000);
     if (want < 2 || os_atomic_load(&processor_avail_count, relaxed) < 2) {
         printf("SWEET HANG GAP: sweethang=1 refused: %u/%u CPUs online, the QR poll thread could not run, not hanging\n", processor_avail_count, want);
         return;
     }
     ```
     Also put `%u/%u CPUs online` into the `SWEET HANG:` line. Whether `processor_avail_count` links from bsd/ is a guess: it
     is declared at T:osfmk/kern/processor.h:419, and its private scope was not checked, so build it. The run plan must
     keep `--cpus 8` (W:docs/runplans/c170-hang-restart.md:31, which it does).

3. **Medium: run plan, no positive evidence of the hang point (c170-hang-restart.md:17-20,25).** USB is down by design, and
   with `--qr 1500` the screen is never taken over (T:sweet_qr.c:262-277), so the run records nothing that proves
   `SWEET HANG: sweethang=1` was reached or that the QR thread was alive. A hang elsewhere would produce the same "no reset"
   result and be read as "the poller does not run during a hang". Examples: an XNU hang between the timer arming and
   T:sweet_ufs.c:671, or a shim hang.
   - Fix: use `--qr 60`. The QR thread polls in the delay loop (:264) for 60 s and then in the takeover loop (:279), so the
     timer is still exercised. The camera snaps then carry `SWEET HANG: sweethang=1 ...` before the +120 s reset.
   - Make Q1's answer column the QR snap line `SWEET HANG: sweethang=1` (snaps/qr2-*), and cite :279 alongside :264 in Q2.
   - Not verified: that xrun's camera decodes QL2 in this configuration (guess; check `snaps/` handling).

4. **Low/Medium: run plan, pass criterion has no time window (c170-hang-restart.md:18,20).** `usb_back` set plus the 4ee0
   landing cannot tell the timer from a panic reset. Patch 0182 makes a panic with no panic region return from
   SavePanicInfo, and `sweet_halt_restart` sends panic types 4 and 9 to `sweet_machine_reset(1)` (T:sweet_restart.c:82-84),
   which is the same fastboot landing.
   - Fix: Q2/Q4 PASS only if `usb_back - t_boot` is ≥ 120 s and ≤ 120 + 180 s (run.json fields, W:tools/xrun_report.py:267).
     A return before +120 s is "reset, not the timer".

5. **Low: doc accuracy, "UFS-init thread" (0191 comment line 13; commit message; run plan :3, :18).** There is no separate
   UFS-init thread. The spin runs in kernel_bootstrap_thread (bsd_init → IOFindBSDRoot), which is pri 95, fixed, and bound
   to the boot CPU (facts above).
   - Fix: say "the kernel bootstrap thread (bsd_init → IOFindBSDRoot → sweet_ufs_init), bound to the boot CPU". Change the
     comment's "Only the other kernel threads ... keep running" to "threads on the other CPUs keep running; the boot CPU
     runs nothing below priority 95".

6. **Low: doc accuracy, sweetlog (run plan :25; docs/research/pr2-panic-reset-path.md:50).** "No `sweetlog=1`" and "needs
   `sweetlog=1`" are both wrong per source. `sweetlog` defaults to on (`on = 1`, T:sweet_ufs.c:1041-1046) and is gated on
   `su.writable` (ufsrw=1, which is in xrun's observed default boot_args).
   - In this run the log thread is absent only because :760 is after the hang.
   - pr2's line cites (sweet_ufs.c:973-974,1020; sweet_qr.c:347) are stale for this tree (poll at :998; the QR polls are at
     :184/264/279, and :347 is `sweet_qr_start`).
   - Fix: reword both, and update the cites.

7. **Low: R8 edge cases (0191:19-26), no fix required, document.** A bare `sweethang` token (no `=`) parses as 1
   (T:bootargs.c getval `*val = 1; return NUM` at ~485) and hangs. `sweethang=abc` copies the string into the uint32
   (bootargs.c:149-152) and prints the GAP line with a garbage number, so it is still loud, not silent. `sweethang=0` is a
   silent off; that is documented and allowed. Fix: the comment should say "bare `sweethang` = 1".

8. **Low: process, the brief/recipe verification command.** `git apply --check -p1 --directory=. P` fails rc=128 (`invalid
   path './bsd/...'`) on any patch. Fix: drop `--directory=.`, as tools/stack-apply:83 does (it uses plain
   `git apply --check`). AP-CANDIDATE: verification command with `--directory=.` always fails [obs this review] | guard:
   none because it is brief text (or a delegate-brief lint).

9. **Low: no host guard on the hook position (0191 hunk 2).** A mutation that moves `sweet_hang_for_test()` after
   `sweet_usb_probe()`, or before `sweet_qr_start()`, passes every host check. Only hardware Q1 would catch it.
   - Fix (optional): a stack test that, in the patched sweet_ufs.c, checks the line order `sweet_qr_start();` <
     `sweet_hang_for_test();` < `sweet_usb_probe();` inside `sweet_ufs_init`, and fails on reorder.

Not verified (guess): CPU scheduling of the QR thread onto a secondary in the edge/clutch pset layout of this port; I
reasoned from source only. Console printf from the QR thread at reset time not blocking with USB down: earlier runs
printed fine from that thread, but never with USB down.
